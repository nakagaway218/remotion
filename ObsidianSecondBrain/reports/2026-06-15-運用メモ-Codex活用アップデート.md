# Codex活用アップデート

## 結論

この資料は丸ごと教材として保管するより、日常運用に効く部分だけを取り込むのがよい。今すぐ効くのは、`/goal` 的な完了条件の明確化と、Browserを使った画面確認ループ。

## 今後の基本運用

### 1. 大きめの作業は「目標」として渡す

単に「直して」ではなく、次を含めて頼む。

- 背景: なぜ必要か
- 対象: どのフォルダ、画面、機能か
- 完了条件: 何ができたら終わりか
- 制約: 触らない場所、守る方針
- 検証: 実行するコマンド、確認する画面
- 成果物: README、レポート、差分説明など

テンプレート:

```text
この作業を目標として進めてください。

背景:
- 

対象:
- 

完了条件:
- 

制約:
- unrelatedな変更はしない
- 個人情報や秘密情報は扱わない

検証:
- 

最後に:
- 変更ファイル、検証結果、残課題をまとめてください
```

### 2. UI作業はBrowser確認を標準にする

フロントエンド、LP、管理画面、教材ビューア、Webarticle、ScenariowritingのUIでは、可能なら次のループを使う。

1. 起動方法を確認する。
2. 開発サーバーを起動する。
3. `@Browser` またはアプリ内ブラウザで対象URLを開く。
4. Desktop幅とMobile幅で確認する。
5. 修正する。
6. 同じ画面を再確認する。
7. 見たURL、画面幅、残課題を報告する。

### 3. Appshotsは「使える時だけ」

Appshotsは画面状態をCodexに渡す考え方として有用。ただし、資料上はmacOS版Codex app中心の機能なので、Windows中心の現在運用では必須にしない。

Windowsではまず次を優先する。

- Codexのアプリ内Browser
- Browser plugin
- スクリーンショット添付
- 必要な場合だけChrome連携

### 4. プラグイン共有とAnalyticsは今は参考扱い

プラグイン共有やAnalyticsは、チーム導入やBusiness/Enterprise運用で価値が出る。個人の `Myownproject` 運用では、まずスキル、`AGENTS.md`、`SKILL.md`、ObsidianSecondBrainで十分。

## Myownprojectでの使い分け

| 場面 | 使うもの |
|---|---|
| 1回限りの小作業 | 通常依頼 |
| 複数ステップの実装 | 目標、完了条件、検証方法を明記 |
| UIの見た目確認 | Browser確認 |
| 繰り返す手順 | `SKILL.md` または専用skill |
| 外部サービス連携 | plugin / connector |
| 長期文脈 | `ObsidianSecondBrain/Memory.md` と `reports/` |
