## 1. CLAUDE.mdとは何か

### 一言で言うと

**Claude Code が起動するたびに自動で読み込む「行動規範ファイル」**。

Markdownで書かれたテキストファイルで、特別な記法は不要。ただし、置く場所と書く内容次第で、Claude の行動が根本から変わる。

### 普通のチャット指示との違い

| 比較項目 | チャット内の指示 | CLAUDE.md |
|---|---|---|
| 有効期間 | そのセッション内のみ | 毎回自動で読まれる |
| 書く場所 | チャット欄 | ファイルシステム |
| 影響範囲 | その会話だけ | プロジェクト全体・全セッション |
| 覚えてくれるか | セッションが終わると忘れる | ファイルが変わらない限り永続 |

チャットで「毎回返答は日本語で」と言い続けている人がいたとしたら、CLAUDE.mdに一行書けば二度と言わなくていい。

### 読み込まれるタイミング

Claude Code を起動してプロジェクトを開いた瞬間、ファイル階層を辿ってすべてのCLAUDE.mdを自動で読む。ユーザーが何も言わなくても、Claude は最初から「このプロジェクトのルール」を知った状態でスタートする。

## 2. なぜこれほど重要なのか

### 「自分専用AI」と「汎用AI」の差

Claude はデフォルト状態では全ユーザー共通の振る舞いをする。英語で返したり、毎回「もちろんです！」と始めたり、必要以上に丁寧な説明をつけたり。

CLAUDE.mdはこれを変える。正確には、**Claude の行動を特定のコンテキストに固定する**。

「YouTubeの台本を書いてほしい」という依頼でも：
- CLAUDE.mdなし → 一般的な構成の台本
- CLAUDE.mdあり → あなたのチャンネルの視聴者層・文体・長さ・禁止ワードをすべて織り込んだ台本

同じ指示から得られる成果が、設定しているかどうかで大きく変わる。

### 永続契約という考え方

CLAUDE.mdは「設定ファイル」と捉えるより、**Claude との永続的な取り決め書**として捉えるのが正確。

チャット内の指示は「今日だけ守ってね」という口約束。CLAUDE.mdは「プロジェクトが続く限り守ってほしい」という文書化されたルール。

重要な判断基準：
- **同じ修正指示を2回以上したことがある** → CLAUDE.mdに書くべきサイン
- **毎回同じ補足説明をしている** → CLAUDE.mdに書くべきサイン
- **「またそれか」と思った瞬間** → CLAUDE.mdに書くべきサイン

### 時間コストの削減

10個のプロジェクトに週20時間Claude Codeを使うとして、毎回の「今日の前提説明」が各セッション3分かかるとすると、週に1時間以上が前置きに消えている計算になる。

CLAUDE.mdを適切に設定することで、これがゼロになる。

## 3. ファイルの種類と読み込み優先順位

Claude Codeが認識するCLAUDE.mdは**3階層**ある。

### 階層構造

```
~/.claude/CLAUDE.md          ← ① グローバル設定（全プロジェクト共通）
~/projects/myapp/CLAUDE.md   ← ② プロジェクト設定（このプロジェクト専用）
~/projects/myapp/src/CLAUDE.md ← ③ サブディレクトリ設定（特定フォルダ専用）
```

**読み込み順**: ①グローバル → ②プロジェクト → ③サブディレクトリ（上書きではなく、全部マージされる）

### ① グローバル設定（`~/.claude/CLAUDE.md`）

全プロジェクトに横断して効くルール。「自分という人間のプロフィール」と「どんな作業でも守ってほしい基本行動」を書く場所。

向いている内容：
- 返答言語（日本語で返す、など）
- フィラー禁止（「了解しました」「もちろん」を禁止）
- 取り消せない操作前の確認要求
- 自己紹介（職業・主な業務）

### ② プロジェクト設定（プロジェクトルートの`CLAUDE.md`）

そのプロジェクト固有のルール。Gitリポジトリに含まれることが多く、チームで共有することもできる。

向いている内容：
- このプロジェクトのコーディング規約
- 使用しているフレームワーク・ライブラリの方針
- ファイル構造の説明
- このプロジェクト固有のNG事項

### ③ サブディレクトリ設定

特定フォルダにだけ適用したいルール。フロントエンドとバックエンドで別のルールを持たせるような使い方ができる。

### 優先度の考え方

矛盾が生じたとき、**より具体的な（下位の）設定が優先**される。プロジェクトレベルでグローバル設定を上書きできる。

## 4. 正しい設計の考え方

### 「自己紹介ではなく行動規範」

よくある失敗：Claude に自己紹介を書く

```markdown
# NG例
私はYouTubeクリエイターです。動画制作をしています。
チャンネル登録者は1万人で、週2本投稿しています。
```

これは状況説明であって、Claudeの行動は変わらない。

正しいアプローチ：行動が変わる指示を書く

```markdown
# OK例
- 台本を書くとき → 視聴者は30〜40代の副業初心者。専門用語を使ったら必ず日本語で説明を入れる
- 動画タイトル案を出すとき → 必ず5案出して、各案に「なぜこのタイトルか」を一行で添える
- 文章の長さ → 台本は7〜10分想定で2000〜2800文字。それ以外は聞かれない限り長くしない
```

### 「追加ではなく変換」として書く

CLAUDE.md は Claude のデフォルト行動を**変換**する場所。デフォルトで既にやってくれることを書き直す必要はない。

「コードを書く」「要約する」「翻訳する」→ これらは指示なしでもやる。書かなくていい。

「毎回確認を取る」「日本語で返す」「出力の末尾にサマリを付ける」→ これらはデフォルトと違うので書く価値がある。

### 200行以内を守る理由

Claude Code はCLAUDE.mdの内容を毎回コンテキストに読み込む。長すぎると：
- 肝心なルールが埋もれて無視される
- コンテキストウィンドウを圧迫する
- 矛盾するルールが生まれやすくなる

目安として**コアルールは200行以内**。超えそうなら、詳細は別ファイルに分けて参照させる。

```markdown
# 推奨パターン：参照構造
- 詳細は `/docs/coding-standards.md` を参照
- note記事の文体規定は `memory/feedback_note_format.md` を参照
```

### Progressive Disclosure（段階的開示）

全部を一枚のCLAUDE.mdに書かない。

- CLAUDE.md → コア原則のみ（常に読まれる）
- 参照先ドキュメント → 詳細ルール（必要なときだけ読まれる）
- memory/ ディレクトリ → セッションをまたぐ記憶・フィードバック

これにより、重要なルールが「埋もれる」リスクを減らせる。

## 5. 書くべき内容・書いてはいけない内容

### 書くべき内容

**① 同じ修正を2回以上した行動**

「毎回これを直している」という体験は、CLAUDE.mdに書くべき最有力候補。

例：
- 「毎回英語で返してくるのを日本語に直している」→ 返答言語を指定
- 「出力の末尾の長い要約を毎回消している」→ 末尾要約禁止
- 「提案してくれるのはいいけど毎回5案多すぎる」→ 案の数を3案に制限

**② 取り消せない操作への制御**

削除・公開・送信・決済など、一度やると元に戻せない操作の前に確認を取らせるルール。

```markdown
- 取り消せない操作の前（削除・上書き・外部送信・公開・課金）→ 必ず確認を取る
```

**③ 業務コンテキストの説明**

Claude が判断に使える背景情報。「なぜこのプロジェクトが存在するのか」ではなく、「この情報があると判断精度が上がる」情報に限る。

```markdown
- このプロジェクトのユーザー層 → 40〜60代の非エンジニア。コードの説明は不要
- メインの投稿媒体 → YouTube + note + X（この順で優先度が高い）
```

**④ 禁止事項（具体的なもの）**

「〜しないで」より「〜するな」の方が守られやすい。

```markdown
# 推奨
- 応答の冒頭にフィラーを入れるな（「了解しました」「もちろん」「素晴らしい」等）

# 非推奨  
- なるべくフィラーは避けてほしいです
```

---

### 書いてはいけない内容

**× コードのパターンや規約（コードベースから導ける情報）**

Claude Code はプロジェクトのコードを読める。「TypeScriptで型を書け」「async/awaitを使え」などは、コードを見れば分かることなので書かなくていい。

**× Gitの変更履歴（git logで分かること）**

誰が何を変えたかは `git log` / `git blame` が正確。CLAUDE.mdに書いてもすぐ古くなる。

**× 一時的な作業状況**

「現在リファクタリング中」「〇月〇日のデプロイに向けて作業中」→ これは会話内で言えばいい。CLAUDE.mdに書くと古くなっても気づかない。

**× すでにドキュメントに書いてあること**

README.mdや公式ドキュメントにある内容の転記は不要。参照させれば十分。

## 6. トリガー→アクション形式のルール術

CLAUDE.mdで最も効果的な書き方は**「トリガー → アクション」形式**。

### なぜこの形式が効くのか

Claude はルールを「状況に応じて適用する」形で処理する。「〇〇したとき → △△する」という形式は、この処理と相性がいい。

曖昧な書き方より、条件が明確な方が守られやすい。

### 基本パターン

```markdown
## ルール名

- [トリガー] → [アクション]
```

### 実例集

**応答・コミュニケーション系**

```markdown
- 応答を始めるとき → フィラー（「了解しました」「もちろん」等）を禁止。回答から始める
- 重要な作業に着手する前 → A案/B案/C案など2〜3の方針を提示し、選択を待つ
- 日付・数値・固有名詞を書くとき → 確証がなければ「未確認」と先に明示する
- 返答の長さ → 質問の重さに合わせる。単純な質問には短く直答する
```

**編集・スコープ系**

```markdown
- 編集タスクを受けたとき → 指示されたセクションのみ触る。隣接箇所の「ついで改善」はしない
- 既存ファイルを大幅に書き換える前 → 何をどう変えるかを予告し、承認を待ってから着手する
- 編集・コーディング完了時 → 末尾に「変えた箇所/触っていない箇所/確認してほしい箇所」のサマリを必ず付ける
```

**安全系**

```markdown
- 取り消せない操作の前（削除・上書き・force push・外部送信・公開）→ 必ず確認を取る
- 外部に出る文章を公開する前 → ファクトチェック + 誇張表現の検出を通す
- 実機検証なしに「動きます」と言わない → 対象環境で動作確認するまで完了報告しない
```

**記憶・記録系**

```markdown
- セッションを開始したとき → memory/MEMORY.mdを読んでから動く
- 同じ詰まり方を2回以上したとき → feedback_*.md（新規可）に必ず記録する
- 「session end」と言われたとき → 次回引き継ぎを memory に書き残す
```

### トリガーを具体的にするほど効果が上がる

| 曖昧（効きにくい） | 具体的（効きやすい） |
|---|---|
| 「気をつけて」 | 「APIキーをコミットする前 → .gitignoreを確認する」 |
| 「慎重に」 | 「本番DBを変更する前 → 必ずバックアップを確認する」 |
| 「品質を大切に」 | 「コードを出力するとき → テストも合わせて出す」 |

### 🎥 YouTubeクリエイター向け

```markdown
# CLAUDE.md — YouTubeチャンネル運用

## 自分のプロフィール（判断に使う情報）
- チャンネルテーマ: [例：副業・AI活用]
- 主な視聴者層: [例：30〜40代の会社員、副業に興味あり]
- 平均動画尺: [例：8〜12分]
- 主な展開先: YouTube → Instagram Reels → note → X

- 台本を書くとき → 視聴者に話しかける口語体。「ですます」調。専門用語は必ず補足説明を入れる

## 禁止
- 「必ず稼げる」「絶対」「100%」等の断定保証表現を書くな
- 外部公開前にファクトチェックを省略するな
```

### 💻 エンジニア・開発者向け

```markdown
# CLAUDE.md — [プロジェクト名] 開発設定

- コードを書くとき → 型安全を優先。anyの使用は禁止

- 本番環境のデータを変更する前 → 必ず確認を取る

## Git
- コミットメッセージ → 「feat: 〇〇を追加」「fix: 〇〇を修正」の形式
- 未確認の変更を本番にデプロイするな
```

## 8. 裏技・上級テクニック

### 裏技① memory/ ディレクトリとの組み合わせ

CLAUDE.mdはルールを書く場所。**記憶は別ファイルに分ける**ことで、CLAUDE.mdを小さく保てる。

```markdown
# CLAUDE.mdに書く参照指示
- セッション開始時 → memory/MEMORY.md を読んでから動く
- 重要な判断をしたとき → memory/decisions.md に追記する
```

`memory/MEMORY.md` には「今週何を決めたか」「プロジェクトの現状」を書く。CLAUDE.mdとの分担が明確になる。

### 裏技② サブディレクトリCLAUDE.mdで文脈を切り替える

```
myproject/
  CLAUDE.md        ← 共通ルール
  frontend/
    CLAUDE.md      ← React + TypeScript 専用ルール
  backend/
    CLAUDE.md      ← Python + FastAPI 専用ルール
  docs/
    CLAUDE.md      ← ドキュメント文体・禁止表現
```

ディレクトリごとに文脈が違うプロジェクトで有効。フロントエンドの開発中はフロントエンドのルールだけが有効になる。

### 裏技③ 「禁止」より「代わりにこうして」

禁止を書くとき、代替行動を一緒に書くと守られやすい。

```markdown
# 効果が薄い
- 長い説明を書くな

# 効果が高い  
- 長い説明は書くな → 代わりに「詳しく知りたい場合は〇〇を参照」と誘導する
```

### 裏技④ 「コア」と「詳細」を分ける2ファイル戦略

```
CLAUDE.md        ← 20行以内のコア原則のみ
CLAUDE-DETAIL.md ← 詳細な補足説明（CLAUDE.mdから参照）
```

コアだけなら毎回確実に読まれ、詳細はタスクに応じて参照される。コンテキストウィンドウの節約にもなる。

### 裏技⑤ スキル・エージェントとの連携

Claude Code のスキル（`/cut` `/srt` 等のカスタムコマンド）との連携をCLAUDE.mdに書いておくと、特定の操作を自動化できる。

```markdown
- 「Xを検索して」と言われたとき → hermes-x コマンドを即実行する
- 動画の文字起こしを頼まれたとき → /srt スキルを使う
```

### 裏技⑥ 「session end」トリガーで引き継ぎを自動化

```markdown
- 「session end」と言われたとき → 次回引き継ぎ（残タスク・決定事項・着手予定）をmemory/handoff.mdに書き残す
```

これにより、セッション終了時に一言言うだけで次のセッションへの引き継ぎが完成する。

### 裏技⑦ 「同じ修正を2回したらCLAUDE.mdへ」ルール

Claude が同じミスを繰り返すとき、それはCLAUDE.mdに書くべきサイン。

```markdown
- 同じ詰まり方を2回以上したとき → feedback_[テーマ].mdに記録し、CLAUDE.mdに要約を追加する
```

このルール自体をCLAUDE.mdに書いておくことで、自己改善のループが回る。

## 9. よくある失敗と対策

### 失敗① 「全部書こうとしすぎる」

**症状**: CLAUDE.mdが500行になって、肝心なルールが無視される

**対策**: 
- コアルールは200行以内に収める
- 詳細は `memory/` や別ファイルに移して参照させる
- 「同じことを2回書いていないか」を定期的に見直す

### 失敗② 「状況説明を書いてしまう」

**症状**: 「私は〇〇という会社で働いています」「このプロジェクトは〇〇のためのものです」と書くが行動が変わらない

**対策**:
- 状況説明は「なぜその行動をしてほしいか」の文脈に変換する
- 「〇〇だから → △△する」形式に書き直す

### 失敗③ 「古いルールが残り続ける」

**症状**: プロジェクトが変わったのにCLAUDE.mdは古い状態のまま。Claudeが古い情報を元に動いてしまう

**対策**:
- セッション開始時に「このCLAUDE.mdは古くなっていないか？」を確認するルールを書く
- `memory/` ディレクトリで時間に依存する情報を管理する

### 失敗④ 「ルールが矛盾している」

**症状**: 「返答は短くして」と「詳細な説明を常に付けて」が同居している

**対策**:
- 新しいルールを追加するとき、既存ルールと矛盾しないか確認する
- 矛盾するルールは、より具体的な（条件が明確な）方を残す

### 失敗⑤ 「グローバルとプロジェクトの混在」

**症状**: プロジェクト固有の設定をグローバルに書いてしまい、他のプロジェクトに悪影響

**対策**:
- グローバル: 「自分」に関すること（言語・フィラー禁止・確認要求）
- プロジェクト: 「このプロジェクト」に関すること（技術スタック・ルール・文体）

## 10. 壁打ちプロンプト：このままClaudeに渡すだけ

以下のテキストをコピーして、Claude Code（またはClaude.ai）に渡すと、対話形式でCLAUDE.mdを一緒に作ってくれます。

---

```
以下の手順で私のCLAUDE.mdを一緒に作ってください。

## あなたの役割
私のCLAUDE.mdを設計するコンサルタントです。
質問しながら情報を集め、最終的にファイルとして保存してください。

## 進行手順

### Step 1: ヒアリング（質問は1回に1〜2つまで）

以下の順番で必要な情報を聞いてください：

1. 職業・業務内容（何のためにClaude Codeを使うか）
2. 主な作業内容（コーディング？文章作成？動画？SNS？）
3. よく使う言語・ツール・プラットフォーム
4. 「Claudeにやめてほしい行動」「毎回修正していること」
5. 取り消せない操作として何が怖いか（公開・送信・削除など）
6. チームで使うか、個人で使うか

### Step 2: グローバルとプロジェクトを判別

集めた情報を整理して：
- どれをグローバル設定（~/.claude/CLAUDE.md）に書くか
- どれをプロジェクト設定（プロジェクトルートのCLAUDE.md）に書くか
を私に確認してください。

### Step 3: ドラフト作成

「トリガー → アクション」形式でCLAUDE.mdのドラフトを作り、私に見せてください。
全体が200行以内になるよう調整してください。

### Step 4: フィードバック

「これで合ってますか？追加・修正はありますか？」と確認してください。

### Step 5: ファイル保存

承認を得たら：
- グローバル設定は `~/.claude/CLAUDE.md` に保存
- プロジェクト設定はカレントディレクトリの `CLAUDE.md` に保存

### 守ってほしいこと
- 質問は一度に1〜2つまで（一気に聞かない）
- 専門用語は使わず、誰でも分かる言葉で
- 「こういう場合はこう書くといい」という具体例を必ず一緒に出す
- 200行以内に収まるよう、書きすぎない

では始めてください。まず、職業と主な業務内容を教えてください。
```
